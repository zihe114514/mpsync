# mpsync 接入指南 —— 让你的客户端 Mod 加入一起听房间

> 面向**其他客户端 Mod / 整合包作者**。读完这份文档，你的 Mod 就能加入 mpsync 房间，
> 与 MuoniumPlayer、Melodify 的玩家在同一个房间里互相点歌。
>
> 参考实现：MuoniumPlayer 的 `mpparty-common/`（本仓已验证可跨房）。
> 协议自 mpsync 1.3.0 起稳定；追加字段向后兼容，破坏性变更会升 `MpProto.VERSION`。

---

## 总览：房间里有什么

一个房间由服务端（mpsync）持有权威状态，所有客户端是它的"瘦终端"：

- **成员表**：房主 / 管理员 / 普通成员，进出房与权限变更都有事件帧
- **歌单队列**：成员点歌进队，按序播放；支持「下一首播放」插队
- **权威时钟**：服务端持有 `pos = now - startEpoch`，客户端据此对齐播放位置
- **播放直链**：谁点歌，谁的客户端解析出音频直链上传，服务端原样转发 —— **你的 Mod 不需要实现任何平台的解析逻辑**，解析复用你已有的取流链路

你的 Mod 需要做的只有四件事：**注册网络通道、收发帧、按房间状态驱动自己的播放器、实现时钟对齐策略**。

## 1. 线协议：一帧 = 一个 JSON

传输层是自定义载荷，**帧格式与平台无关、跨版本逐字节相同**：

- 分帧：varint 长度前缀 + UTF-8 JSON 正文（varint 自己写，别借 Minecraft 缓冲类 ——
  这是跨版本逐字节兼容的第一条纪律）
- 一帧一个 JSON 对象。**未知字段必须忽略、新字段只追加**：两侧各自升级不炸房
- 每帧带 `seq`（服务端发出的命令帧单调递增）——客户端用它丢弃乱序命令

协议常量与已知平台令牌表见服务端 `core/net/Proto`（`KNOWN_SOURCES`：
`netease` / `qq` / `kugou` / `gd` / `bilibili` / `youtube` / `kuwo` / `migu` /
`qianqian` / `soda` / `fivesing` / `jamendo` / `joox` / `apple` / `customapi`，
不限于它们）。你的 Mod 支持新平台，自定一个令牌发上来即可，服务端默认不限制。

### 客户端 → 服务端（C2S）

| 动作 | 要点 |
| --- | --- |
| 进房 | 带邀请码与服务端给的会话信息；服务端回成员表全量 |
| 点歌 | 上传 `平台令牌 + 歌曲 ID + 标题/歌手/时长元数据 + 音频直链`。**直链为空也允许**：服务端会向已在线的其他客户端广播"求链接"，拿到后补传（见 3.2） |
| 播放控制 | 房主/管理员：暂停、恢复、上下曲、seek、循环模式；普通成员发这些帧会被服务端拒绝并提示 |
| 心跳回应 | 见 3.1 |

### 服务端 → 客户端（S2C）

| 帧 | 客户端该做什么 |
| --- | --- |
| 成员/权限变更 | 刷新成员表 UI |
| 队列变更 | 刷新一起听歌单 UI |
| **命令帧**（起播/暂停/seek/切歌…） | **立即执行，不走时钟对齐判定**；帧里带歌曲元数据与直链 |
| **时钟心跳**（带 `heartbeat: true`） | 只用于对齐，绝不当命令处理 —— 见 3.1 |
| 求链接（`waitingUrl`） | 本地恰好有这首歌的可用直链就补传（你解析过、还在缓存里） |

> ⚠️ **C2S 与 S2C 必须是两条独立通道**。1.20.1 Forge/NeoForge 曾因两条方向接了同一个
> 监听器类型导致「服务端发的话客户端全聋」——注册时逐方向核对事件类型。

## 2. 通道注册（按加载器）

通道 ID 与协议版本协商由服务端 `hello` 帧完成，你的 Mod 只需注册收发。

| 加载器 | 通道形态 | 备注 |
| --- | --- | --- |
| Fabric 1.20.1 | 裸 `PacketByteBuf`（Yarn 名） | 无 `CustomPayload` 抽象 |
| Fabric 1.21.1 / 1.21.11 | `CustomPayload` | 三方注册表 |
| NeoForge 1.21.1 / 1.21.11 / 26.2 / 26.3 | `CustomPacketPayload`（官方名） | 与 Fabric 同形 |
| Forge 1.20.1 / 1.21.1 | `SimpleChannel` **不要用** | 它会给负载加一个判别字节，破坏逐字节兼容；用裸 `eventNetworkChannel`（`NetworkRegistry.newEventChannel` / `ChannelBuilder` 链式，两种等价形态都行） |
| Paper / 服务端插件 | Bukkit 消息通道 | mpsync 侧已封装 |

版本相关代码建议**按版本树各写薄薄一层**（通道注册 + 事件挂点），协议与房间逻辑全放
版本中立的一份源码里 —— 参照 MuoniumPlayer 的 `mpparty-common/` + 各树 `party/net/MpNet.java`
结构。跨版本帧逐字节兼容已经由服务端保证，你的适配层保持"只搬字节"即可。

## 3. 时钟同步：这是听感成败的地方

全房一起听的"一起"，取决于你的客户端怎么消费服务端时钟。照抄下面这套（与
MuoniumPlayer 的 `MpSyncPolicy`、Melodify 的 `PartySyncPolicy` 完全一致），不要自创：

### 3.1 播放头对齐

服务端每帧带 `serverTime` 与位置。**用发送时刻补单向延迟，不要相信本地到达时间。**

三档判定，全部由服务端在 `hello` 里下发阈值（老客户端读不到就用相同默认值）：

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `softDriftMs` | 2500 | 偏差小于它：什么都不做 |
| `hardDriftMs` | 6000 | 偏差超过它**且连续 `driftConfirmHits`(2) 次心跳都超、距上次硬跳 > `resyncCooldownMs`(10000)`：才真跳一次 |
| `clockGraceMs` | 4000 | 命令帧之后服务端静默不发心跳的窗口（服务端行为，客户端只需遵守"命令帧立即执行"） |

**为什么这么严**：换歌/暂停后的几秒全房都在开流，位置天然是散的；这时若一偏差就 seek，
seek 又触发重新开流，下一发心跳偏差更大 —— 正反馈死循环，实测"进度来回跳"就是这么来的。
软区间不动作、硬区间要连续确认 + 冷却，就是为了掐断这个环。

### 3.2 求链接 / 补链接

点歌者可不上传直链（比如解析还没完成）。服务端进入 `waitingUrl` 会向其他客户端广播：
**本地缓存里有这首歌可用直链的客户端补传一条**。等待上限 `urlWaitTimeoutMs`（默认 20s）。
你的播放器若缓存了直链，务必实现补传 —— 这是"会员帮全房解流"体验的一半。

### 3.3 试听拦截

服务端会拒绝"链接实际时长 < 歌曲时长 × `minStreamDurationRatio`(0.8)"的帧（防试听片段）。
你上传前自查一遍可减少无谓失败；**90 秒以上的流视为完整歌**，不必再判（两个接口的时长
元数据能差 20%，纯比例误判会误伤完整版）。

## 4. 房间模式下的播放器行为

进房后，你的播放器要交出部分本地控制权（MuoniumPlayer 的做法，建议照搬）：

- 「下一首播放」→ 变成房间点歌；本地队列让位于房间队列
- 播放/暂停/上下曲/进度/播放模式键 → 变成房间指令；普通成员按键时给出
  "只有房主或管理员可以…"的提示，**不要静默失败**
- **不要另开通路**：房间下发的链接注入你既有的取流环节即可 —— 下载、容器识别、
  转码、封面、歌词、通知全部照常工作
- 歌曲元数据（标题/歌手/时长/封面）房间帧里都有，拿来直接铺 UI

## 5. 最小接入清单

- [ ] C2S / S2C 两条通道，逐方向核对监听事件类型
- [ ] varint 分帧自实现；JSON 未知字段忽略
- [ ] 进房 / 退房 / 成员表 / 队列帧处理
- [ ] 命令帧立即执行；心跳帧走三档对齐（阈值读 `hello`，默认值与服务端一致）
- [ ] 点歌帧上传平台令牌 + ID + 元数据 + 直链；实现 `waitingUrl` 补传
- [ ] 房间模式接管本地传输控制，权限不足给出提示
- [ ] `MpProto.VERSION` 与服务端一致才进房（协商失败给出"客户端/服务端版本不匹配"提示）

**自测三件事**：与 MuoniumPlayer 同房互听；服务器 1.21.1 + 客户端 1.20.1 跨版本进房；
拔网线 10 秒再插回（验证冷却期内不疯狂 seek）。
